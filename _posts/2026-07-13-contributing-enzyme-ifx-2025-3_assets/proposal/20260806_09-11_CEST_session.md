## 2. How the tendencies reach the model state

1. `gwdrag_wms` writes momentum tendencies `ptenu`→`prm_nwp_tend%ddt_u_gwd`, `ptenv`→`ddt_v_gwd`, plus fluxes `pfluxu/v` (`mo_nwp_gw_interface.f90:256-259`). Post-processing caps them at `|tend|≤0.05`, scales level 1 by 0.125, applies SPPT (`:268-306`).
2. `nwp_nh_interface` accumulates **wind** tendencies: `z_ddt_u_tot = ddt_u_gwd + raylfric + ddt_u_sso + ddt_u_pconv` (`:2454`).
3. **Temperature** path (only if `itype_dissip_heat≥1`): `z_ddt_temp_drag = -rcvd * (u·(sso+gwd+raylfric)+…)` → summed into `z_ddt_temp` (`:2495-2503`).
4. `z_ddt_temp` → converted to Exner tendency `pt_diag%ddt_exner_phy` (`:2614`).
5. Cell wind tendencies `z_ddt_u/v_tot` are interpolated to edges → `pt_diag%ddt_vn_phy`; with turbulence active, `pt_prog%vn` is directly updated by `dt_loc` (`:2844-2865`).
6. **Dynamical core consumes them:** `solve_nh` adds `ddt_vn_phy` to the velocity update (`mo_solve_nonhydro.f90:1365,1410`) and `ddt_exner_phy` to the Exner/thetav/pressure update (`:2316,2340,2574`).
7. GWD tendencies also feed **turbulence** (`turbdiff`) dissipative-heating branch (`mo_nwp_turbdiff_interface.f90:563-564`).

So zonal/meridional wind (u,v) enter state via `ddt_vn_phy`→`vn`; temperature via `ddt_exner_phy`; the fluxes `pfluxu/v` are diagnostics saved to `ztot` locals only.

## 9. Features that may complicate Enzyme

1. **Module globals (largest issue).** `data_gwd` variables read inside the kernel without appearing in the argument list. Enzyme must either treat them as differentiable tape nodes fed from init, or they must be lifted to dummy args. Same for `atm_phy_nwp_config`, `phy_params`, `vct`. These are write-once-at-init so lifting is *cleanly possible*.
2. **OpenMP / OpenACC.** Directives pervade every level (both `!$OMP` and `!$ACC`, `__acc_attach`, device data regions). The natural AD strategy is the **serial CPU path** (treat `lacc=.FALSE.`), since the loops are "flat" (GANG/VECTOR = parallelism, not control-flow). GPU differentiation is a much harder ask.
3. **Function pointers.** Almost none in the GWD path itself; but the *full* suite brings in **rte-rrtmgp/ecrad**, which dispatch optics/model through function pointers — genuine AD impedance for the "entire physics suite" boundary.
4. **Recursion.** None observed.
5. **Aliasing.** Heavy use of `TARGET`/`POINTANT`, `ASSOCIATED`, `CONTIGUOUS`, derived types, and **array-section aliasing** (e.g., `pt_diag%temp(:,:,jb)` passed as assumed-shape actuals; `prm_nwp_tend%ddt_u_gwd` written while `pt_diag` read). Also in-place state updates `vn(nnew) = vn(nnow)+...`. Works be careful about activity/aliasing analysis. The tendency arrays are read-only-output, so aliasing is mostly benign but flagged.
6. **External library/boundary calls:** MPI halo exchanges (`sync_patch_array*`), `dr_hook` profiler, `mtime` datetime, `COMIn` callback (`icon_call_callback`), YAC coupling, timer framework. Need to provide adjoint/tangent stubs or differentiate through them.

Recommendation: **diff a single column slice** (fixed `j`) with `lacc=.FALSE.`, on serial CPU — that yields a clean scalar/vector kernel for a first Enzyme pass.

## 10. Four differentiation boundaries

### A. Only `gwdrag_wms`
- **Derivatives:** `∂(ddt_u_gwd,ddt_v_gwd)/∂(u,v,T,pres,geo,lat,precip,klaunch, gfluxlaun, gcstar, …)`. Exact per-column Jacobians of the WG scheme.
- **Scientific questions:** which input states/tunables most affect the drag tendencies — sensitivity & parameter optimization (Ern/C-star tuning), local observability, critical-layer sensitivities.
- **Refactoring:** mild. To get tune sensitivities through AD you **must lift `data_gwd` variables (gfluxlaun, gcstar, etc.) into dummy args** (they're module globals). Otherwise the kernel is already a clean pure-function and works out of the box.

### B. Complete GWD package (`nwp_gwdrag` + both schemes)
- **Derivatives:** adds orographic (SSO) response and the post-cell caps/SPPT: `∂(ddt_u_sso+v_gwd, …)/∂(ext-data orography, sso tuning, gwd tuning, precip, lat)`, and (via `turbdiff`) `∂(dissipative T)/∂u,v`.
- **Scientific questions:** coupled non-orog+orog drag; crosstalk between the two schemes; ensemble-sensitivity to `tune_gfluxlaun` perturbations.
- **Refactoring:** yes — both `gwd_wms` and `sso` read module state (`data_gwd`, SSO tuning, `phy_params`, `vct_a`), so the same arg-lift applies; also trim boundary calls (`sync`, `COMIn`) from the AD region.

### C. Entire physics suite (`nwp_nh_interface`)
- **Derivatives:** full Jacobian of *all* physical tendencies (radiation, convection, microδryption, turbulence, GWD, cloud) w.r.t. the full prognostic input state; and inter-scheme couplings (e.g., GWD↔turb dissipative heat, convection↔precip→GW launch).
- **Skills:** whole-physics parameter sensitivity; consistent coupled-tendency gradients for data assimilation (e.g., adjoint-based forecast-sensitivity), tangent-linear for physics-only linearized experiments/SKEB.
- **Refactork:** significant. You'd be forced to thread threading the AD region across 500+ routines, eliminating module globals and pointer-aliasing, stubbing MPI/`sync`/`mtime`, and crossing the function-pointer radiation scheme — a substantial engineering project.

### D. One complete ICON timestep (physics + dynamics `solve-nh`)
- **Derivatives:** the full **model tangent propagator** `∂state(n+1)/∂state(n)` through one RK step (advection+Coriolis+pressure gradient+dynamics+all physics+filter/IAU).
- **Skills:** finite-time Jacobian of the NWP forecast operator → the core of 4D-Var adjoint, tangent-linear for EPS/perturbation growth, linear stability, and reduced-dim transformations. This is the ultimate target.
- **Rounds-fans:** largest — must bridge physics *and* dynamics scheduling, halo-exchange/MPI, **the whole evaluate-model state**, then time-stepping control flow (`integrate_nh`, `perform_nh_*loop`), and non-differentiable branches (IFAM critical-level `SIGN(MIN())` etc.). Realistically requires a staged approach, and likely a compiled adjoint rather than pure Enzyme on the full model.

**Bottom line:** A (just `gwd`, with module globals lifted) is a small, achievable first Enzyme milestone; B is a natural science-useful package boundary; C and D are model-engineering projects needing extensive refactoring (arg-list exposure of module globals, stripping of MPI/OpenACC/COMIn/dr_hook and the radiation function-pointer scheme).
