Question @Jared, all: how much slower is running the AD code? I expect factor 5 to 10. I suppose we will only run this to learn about sensitivities and conduct the production runs with regular fast Intel compilation? Should the Intel compiler be the same? So would we use IFX for everything?

Whether we use IFX or Flang is discussed a bit in the Code Bottlenecks section. With respect to the slowdown from running AD, it’s difficult to estimate since it would depend on a number of factors like: (1) whether forward or reverse AD is used; (2) number of inputs (n) to a function compared with outputs (m) (e.g., forward mode AD is really slow when n >> m); (3) the complexity (e.g., lots of branching) of the routine that gets autodiffed. To make this a bit more concrete, there may be a negligible effect on runtime when autodifferentiating with respect to independent variables representing single parameters (e.g., ∂(ddt_u_gwd)/∂gfluxlaun from mo_gwd_wms.f90 and mo_nwp_gw_interface.f90) that are tunables/constants since only a single reverse pass would be needed. However, if the independent variable of interest are model state (e.g., ∂(ddt_u_gwd)/∂u) then slowdown may be more significant. This would require benchmarking.

@Claudia, here are some code bottlenecks/considerations:
Compiler compatibility:
IFX v2025.3 is a currently supported ICON configuration and that has an LLVM backend so it could be used to produce LLVM IR that Enzyme can autodiff. However, Intel compilers are a black box and changes to Enzyme to support IFX 2025.3 would 	require reverse engineering the LLVM IR emitted by IFX. This is a very challenging task. Conversely, Flang is open-source but does not yet compile the complete ICON code 	base (apparently there are dependencies that don’t compile). I have been told by Dr. Georgiana Mania (DKRZ) that there is ongoing work at DKRZ is improving Flang configuration, but this is still an open question and I will get details from them. I think this is probably the biggest technical challenge to getting Enzyme to work with such a large codebase. Mentioned in EnzymeAD:pull#2987. Intel compilers are quite famous for their strong performance (and also infamous for their annoying bugs), so if we end up going the Flang route, which is comparatively a less mature compiler, we will definitely see slowdown (independent of Enzyme).
 	
Suitable build system modifications:
It is worth noting that since Enzyme is a compiler plugin, we cannot simply add the appropriate compiler and link flags to ICON’s build system in order to use it. ICON has quite an extensive, legacy build system written in GNU Autotools that would have to be modified accordingly. With LLMs, maybe not a big challenge, but worth considering.
 	
Code structure for differentiation:
We know that Enzyme differentiates the LLVM representation of the program, but useful gradients require that quantities of interest are exposed in the computational graph. 	My understanding is that certain parameters of interest (e.g., parameters in a gravity wave drag parametrization such as gfluxlaun, see mo_gwd_wms.f90) that might be module level constants should be refactored such that they are inputs to the function of interest. For example,
 	
 	
SUBROUTINE 	gwdrag_wms(kidia, kfdia, klon, …)
	
	should be changed to something like
	
	SUBROUTINE 	gwdrag_wms(kidia, kfdia, klon, gfluxlaun, ...)
Such a change is trivial in this case, but it illustrates that one must invasively—though not substantially—alter parts of the codebase. In theory, one could attempt to autodiff the ICON time step scheme, but the complexity of the ICON codebase would make this likely extremely challenging. So it is important to be reasonable about the scope of functions that you want to autodifferentiate. Subroutines in self-contained parametrizations (e.g., gravity wave drag, ion drag, etc.) are likely the easiest initial choices.
Parallel execution:
Enzyme has tests demonstrating support for parallel programming constructs such as MPI and OpenMP primarily in the context of C programs. However, at the moment there are not MPI Fortran integration tests OpenMP Fortran tests, see EnzymeAD:issues#3066 and EnzymeAD:issues#3065, and this might imply that when scaling up and attempting to autodiff more complicated routines, that other challenges could arise. In principle, the existing test suite should cover many of our use cases, but given the scale of ICON’s codebase, it would be unsurprising not to run into some challenges here.
